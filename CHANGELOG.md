### Added
- **CI (`.github/workflows/ci.yml`), 2026-08-22.** Runs `ruff check .` + `pytest` on every push/PR to `main`/`dev`. Separate from `update-daily.yml`/`update-hourly.yml`, whose `workflow_dispatch`-only schedules are untouched — local launchd stays primary, Atlas the manual fallback. No MongoDB is provisioned: every test is a pure function or mocks ccxt/MongoDB, so the whole suite runs unmodified in CI. Added `pyproject.toml` (`[tool.ruff]` config only — this repo still installs runtime deps via `requirements.txt`, not packaging metadata) and `requirements-dev.txt` (`ruff==0.9.10`, matching the pin already used by `eeva-dca`/`eeva-exec`). Repo was lint-clean at 0 errors after enabling ruff: 49 pre-existing issues auto-fixed (import sorting, unused imports, useless f-strings — mechanical, behaviour-preserving, verified against the full test suite), 2 ambiguous `l` variables renamed to `low` in `extract.py`/`extract_perp.py`, and a small set of pre-existing issues (line-length in the indicator glossary and Telegram-message strings, `sys.path.insert()`-before-import in `bin/*.py` entrypoints, one lambda-assignment in `indicators.py`) scoped out via `per-file-ignores` with reasons rather than fixed as a side effect — `indicators.py` in particular is the ADR-001 public-API-values file and was deliberately left untouched (R10).
- **Shared KuCoin-429 retry helper (`btc_tracker_mongodb/retry.py`), 2026-08-22 (audit rec #6).** `extract.py`'s spot fetcher retried 3× with exponential backoff on KuCoin's misclassified `429000` rate-limit error (CCXT surfaces it as a generic `ExchangeError`); `extract_perp.py`'s perp OHLCV and funding-rate fetchers had no retry at all, so a rate-limit hit failed hard where the equivalent spot call self-healed — `lean_pipeline.py` having to invent its own `_retry()` around the perp fetchers was direct evidence of the gap. Extracted `call_with_kucoin_retry()` as one shared helper (rather than a second copy-pasted implementation) and wired it into all three call sites: `extract.fetch_candles`, `extract_perp.fetch_perp_candles`, `extract_perp.fetch_funding_rate_history`. `lean_pipeline._retry()` is intentionally left as-is — it's a broader, general-purpose retry for bulk backfill and now simply wraps an inner call that also self-heals. +11 tests (115 → 126): `tests/test_retry.py` for the helper directly, plus retry-path coverage added to `tests/test_extract_perp.py`.

### Changed
- **`requirements.txt` pinned to exact installed versions + `requirements.lock` added, 2026-08-22 (audit rec #2, sev HIGH).** Previously only `ccxt==4.5.40` was pinned; `pandas`, `pandas-ta-classic`, `numpy`, `pymongo`, `python-dotenv`, `requests`, `flask`, `gunicorn`, `mcp`, `pytest` all floated. This repo's indicator COLUMN NAMES are a declared public API (ADR-001) shared with `Crypto_Research_Assistant`, but `pandas-ta-classic` (and the `pandas`/`numpy` arithmetic under it) computes the VALUES stored under those names — a floating version could silently change indicator values across all four independent install surfaces (local venv, the two `workflow_dispatch` GitHub Actions workflows, the Dockerfile) while column names stayed identical, so nothing downstream would notice. All runtime deps now pinned `==` to the venv's known-good versions; `requirements.lock` is the full `pip freeze` reference to diff against before any future bump. `ccxt==4.5.40` and its "v4.5.41 has a packaging bug" rationale preserved unchanged.

### Changed (ops)
- **`com.eeva.tracker-daily` installed at 03:10 local (was 01:10), 2026-07-19.** launchd fires on *machine local* time, so 01:10 was 00:10 UTC under CET but **23:10 UTC under CEST** — the wrong side of the UTC day boundary for half the year, which is what caused the truncated-candle defect. Any local hour 02:10-22:00 is past the boundary in both DST regimes. **Correctness no longer depends on this** (the code refuses to write an unclosed candle, and `run_hourly` closes the daily bar at 00:05 UTC year-round) — the schedule change buys freshness. Previous plist backed up to `/tmp/tracker-daily.plist.bak`.

### Fixed
- **Weekly updates stalled for three weeks on a Monday/Thursday anchor mismatch (2026-08-09).** A regression from the in-progress-candle fix below. `_floor_timestamp` floored `1w` to **Monday** 00:00 UTC — the ISO convention, and what Binance/TradingView use — but KuCoin buckets weekly candles by **epoch modulo**, and the Unix epoch (1970-01-01) was a Thursday, so its weeks open Thursday 00:00 UTC. Every stored weekly bar satisfies `ts % 604800 == 0`; ccxt does the same in its own `round_timeframe` and [deliberately never re-cuts venue boundaries](https://github.com/ccxt/ccxt/issues/25046), so what the seed/backfill paths store is whatever KuCoin served, unnormalised. `_last_closed_period` therefore returned a cutoff **4 days behind** the newest stored bar, `run_update` computed `fetch_from = last_stored + 1w` as greater than it, and took its "up to date" early-return without fetching. Measured on 2026-08-09: `stored 07-23 (Thu)` vs `last_closed 07-27 (Mon)`, `fetch_from 07-30` → nothing fetched. **Not a hard deadlock** — the cutoff advances on Mondays, so it self-cleared roughly weekly and settled into a rolling ~1-2 week lag; all 17 spot-weekly collections sat at `2026-07-23`. Fix: floor `1w` by epoch modulo instead of weekday. Perp weekly shares the code path but is unaffected in practice (`1w` is spot-only in production — KuCoin Futures has no weekly). `TIMEFRAME_GLOSSARY["1w"]["description"]` corrected too: it asserted "Monday open to Sunday close" and is synced to Mongo as shared-contract metadata. +6 tests (90 → 96), including the epoch-alignment invariant and a regression pinning the exact stalled state. **Went unnoticed because `run_watchdog.py` excludes weekly** — see the known issue below.
- **Every write stored an in-progress candle and froze it (2026-07-19).** `run_update` used `_floor_timestamp(now)` — the start of the candle currently *forming* — as the fetch-window bound and never filtered the fetched rows, so each run wrote a partial candle. The next run's gap check saw that timestamp as already stored and skipped it, so it was never corrected. **Measured against KuCoin's own candles (BTC daily, 291 bars): 76% of the 112 bars since the 2026-03-29 DST change have a wrong Close (mean 19.3 bps, max 143 bps) and 12% miss the true high or low** — 2026-07-16 stored Low 63,859.2 against a true 63,750.0, the day's actual low having fallen in the final 50 minutes. The 1h collections were worse: the hourly job runs at :05, so each hourly bar was frozen with ~5 minutes of trading in it (verified live — the stored "latest" 1h row was always the forming hour). The seasonal split is the mechanism: launchd fires on **machine local** time, so the daily job's 01:10 slot is 00:10 UTC under CET (writes the completed previous day, correct) but 23:10 UTC under CEST (writes the open current day). New `_last_closed_period()` / `_drop_unclosed()`; `run_update` and `run_perp_update` now bound the fetch window by the last *closed* period and filter the fetched frame as well (an exchange may return a candle we did not ask for). Affects all timeframes — the root cause was shared code, not daily-specific. +16 tests (74 → 90).

### Added
- **`--refresh-last N` on `update.py`** — also re-fetch and overwrite the most recent N **closed** candles even though they are already stored. The gap check only ever looks at the newest stored timestamp, so a candle the exchange later revises could never be noticed. Wired as `--refresh-last 2` into `bin/run_daily.py` and `bin/run_hourly.py`: a rolling two-period self-heal that also repairs the hand-over (the last partial bar written by the old code is already stored, so the gap check alone would freeze it wrong forever). Older history is untouched — see the note on backfill below.
- **`bin/run_hourly.py` now also closes the daily and weekly bars.** `run_update` returns before fetching unless a new period has closed, so on 23 of 24 runs these steps are a no-op. What they buy is schedule independence: the completed daily bar now lands at **00:05 UTC year-round**, regardless of what local hour the daily job happens to fire at under DST.
- **`deploy/com.eeva.tracker-{daily,hourly,watchdog}.plist` captured into version control.** These existed only as real files in `~/Library/LaunchAgents/` with no source of truth. `tracker-daily` Hour changed 1 → 3 (01:10 local was 23:10 UTC under CEST; any local hour 02:10-22:00 is past the UTC boundary in both regimes). Correctness no longer depends on this — it is a freshness change. **Not installed** — install instructions are in each plist header.

- **The watchdog measured freshness against the wall clock, so it was only correct at one hour of the day (2026-08-09).** `run_watchdog.py` compared `now − bar_timestamp` to a fixed threshold. A bar is stamped at the *start* of a period that closes one period later, so its timestamp age oscillates by a full period between writes — daily 25h→49h, weekly 7→14 days. The 36h daily threshold therefore passed only because the job runs at 05:00 UTC, where the age happens to be ~29h. Run at 21:28 UTC against healthy data it reported **34 daily collections stale and fired a RED Telegram alert with nothing wrong** — measured, not hypothetical; it is how the weekly stall above came to be investigated. Replaced with `periods_behind(latest, now, tf)`, which compares against `_last_closed_period` and is invariant to the hour it runs at: a collection written on schedule reports 0 behind at every hour of its period. Thresholds are now whole periods of grace (`MAX_PERIODS_BEHIND`) rather than hours. `periods_behind` is public and lives beside `_last_closed_period` deliberately — computing "when did a period close" a second time in the monitoring script is how you get two disagreeing notions of a boundary, which is precisely the defect fixed above. Funding stays on a wall-clock bound (8h period against 36h absorbs the oscillation with room to spare). Same run, same data: old check 34 false positives, new check 5 true positives. +6 tests (96 → 102).
- **Weekly is monitored again.** `("1w", "spot")` added to the watchdog, allowed 1 period behind. It had been excluded with a comment dismissing the staleness as a *"pre-existing inconsistency … unrelated to the watchdog's purpose"* — that dismissal was the bug report, mis-triaged, and the exclusion is why the anchor stall ran three weeks unseen. **This will alert.** Five collections are genuinely stale for the separate reason below — `sol` (2 periods), `pepe` (6), `sui` (7), `wif` (17), `wld` (17) — and will appear in the daily RED until that is fixed. They are true positives and are deliberately **not** suppressed: an exclusion added to quiet a known-noisy signal is what removed the only thing that would have said the noise had become a fault.

- **Short-history tokens could never have a bar written — an unguarded None, not a NaN rule (2026-08-10).** Three stacked defects, and the first two are crashes rather than the filtering issue previously assumed here.

  **(1) A crash.** `ta.ichimoku` returns a tuple whose FIRST ELEMENT is None when the series is shorter than senkou (52). `_compute_ichimoku` guarded the tuple — neither None nor empty in that case — then dereferenced the element, so `compute_all` raised `AttributeError` and the token's whole update died. Every other helper in `indicators.py` guards the object it dereferences; this was the only one guarding the container. It read as a warmup quirk because pandas_ta's own `Series has N rows but indicator requires at least 52. Returning None.` sits immediately above it in the log.

  **(2) A second crash, deeper.** `ta.*` helpers return None on short series, and `df[col] = None` assigns that scalar to every row — an OBJECT column of Nones rather than a float column of NaNs. `_compute_ml_features` then ran `df["RSI"].diff(3)` on it: `TypeError: unsupported operand type(s) for -: 'NoneType' and 'NoneType'`. Measured: **every frame of 4–13 rows crashed** (2–3 and ≥14 were fine). Reachable in production — wif's weekly window is 4 stored rows, so one new candle makes a 5-row frame. Fixed once at the boundary (`_coerce_numeric_columns`) rather than at ~30 assignment sites, because NaN is also the semantically correct value: it means "not enough history yet", which the pipeline already treats as warmup.

  **(3) The skip rule manufactured permanent holes.** A row was dropped if ANY validatable column was NaN. `_validatable_cols` already excluded entirely-NaN columns "so they don't cause all rows to be dropped" — the same failure mode, handled one step short: a column with a single valid value (SMA_50 over a 50-row frame) still blocked the other 49. Since `run_update` writes per timestamp and the gap check reads only the NEWEST stored one, a dropped row became permanently unreachable. Of SUI's seven pending weekly bars, six were dropped and the seventh written; sol's series shows the result (`04-02 → 05-14 → 06-18 → 07-16`). Now only NaNs at or after a column's first valid index count as anomalies — warmup NaNs write, which is what `docs/ARCHITECTURE.md` has always documented for newer tokens ("SMA_200/EMA_200 null until ~200 weeks history").

  Verified against live data — pending weekly bars that would now be written, previously **zero for all five**: sol 2, pepe 6, sui 7, wld 17, wif 15 of 17. BTC/ETH unchanged. +13 tests (102 → 115), covering the 4–13 row crash band and a regression pinning SUI's real state.

### Known issue (not fixed)
- **wif still skips 2 of its 17 pending weekly bars.** `Supertrend_Value` is `0.0` on the frame's first row, then NaN for five rows, then real values. That degenerate leading zero makes `first_valid_index()` point at row 0, so the genuine warmup NaNs after it read as interior anomalies. A pandas_ta quirk on a 21-row frame for a stateful indicator, not a flaw in the warmup rule — deliberately not special-cased, since loosening the rule to swallow it would weaken the anomaly detection that is its entire purpose.
- **Historical rows remain truncated.** Fix-forward only, by decision: correcting stored history means rewriting `{token}_{tf}_price_data`, the shared contract collection every repo reads, and would invalidate every metric already computed from it. Note `backfill.py` **cannot** do this repair — its merge is `pd.concat([df_exchange, df_existing])` with `keep="last"` (`pipeline.py:311-317`, `:641-647`), so already-stored data always wins on a timestamp collision; it fills gaps but never corrects a row. A real repair must also recompute indicators forward ≥ `SLIDING_WINDOW` (200) periods, and daily/weekly `VWAP` is a `cumsum` over all prior rows.

## [0.2.0] — 2026-04-26

### Fixed
- **Funding rate silent staleness (KuCoin ~2-day API dead zone).** `run_perp_update` derived the funding fetch `since_ms` from the OHLCV candle gap (= yesterday). KuCoin's `fetch_funding_rate_history` silently returns 0 records when `since >= (now − 2d)`, so funding data stopped accumulating after the initial seed. Root consequence: `funding_rate_ma_7d` went NaN after 7 days and CRA defaulted regime to BEAR, masking the real market signal. Fix: `_get_funding_since_ms()` looks up the last stored funding timestamp from MongoDB and subtracts a 3-day buffer, always landing outside the dead zone. Upsert idempotency absorbs the daily overlap. Manual backfill executed 2026-04-26 (27–54 records per token, 9-day gap closed). 9 new tests.
- **`_fetch_and_store_funding` silent empty result.** Previously logged nothing when the API returned 0 records, making the bug invisible in daily logs. Now logs `No new funding rate records (KuCoin returned empty)`.

### Added
- **Watchdog covers funding_rate collections.** `run_watchdog.py` now checks all 18 `{token}_funding_rate_data` collections with a 36h threshold (same as daily OHLCV). Previously the watchdog only checked 72 OHLCV collections and reported GREEN while funding data was 9 days stale. Checked total is now 90.
