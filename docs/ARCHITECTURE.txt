**Only closed candles are written.** `run_update` bounds its window by
`_last_closed_period()`; before 2026-07-19 it stored the forming candle and the
gap check then skipped it forever. Indicator column names are a public API —
renaming one is a cross-repo change ([ADR-001](../../docs/decisions/001-indicator-columns-as-public-api.md)).

## Data Pipeline

Every token and timeframe runs the same seven steps, orchestrated by
`pipeline.py`. Pick a flow to walk it.

[diagram] One incremental run, for one token and one timeframe.
  - Load window — last 200 rows (a database, table, queue or bucket)
  - Detect gaps — newest stored vs now (code in this repo)
  - Fetch candles — KuCoin via CCXT (something you do not control)
  - Append — onto the window (code in this repo)
  - Recompute indicators — compute_all (code in this repo)
  - Fear and Greed — alternative.me (something you do not control)
  - Bulk upsert — new rows only (a database, table, queue or bucket)
  - Load window -> Detect gaps
  - Detect gaps -> Fetch candles
  - Fetch candles -> Append
  - Append -> Recompute indicators
  - Recompute indicators -> Fear and Greed
  - Fear and Greed -> Bulk upsert

[flow] An incremental run
  1. load — The last 200 rows come back as a sliding window — enough for every indicator's warmup without loading the whole collection.
  2. gaps — The newest stored timestamp is compared against now. Only the difference has to be fetched; everything else is already correct.
  3. fetch — Missing candles are pulled from KuCoin via CCXT (extract.py), bounded by _last_closed_period() so a forming candle is never stored.
  4. append — New candles join the window DataFrame. Nothing is written yet.
  5. indicators — indicators.compute_all() recomputes every column over the window. It is the single source of truth — no other code may produce an indicator.
  6. fng — The Fear & Greed Index is fetched separately from alternative.me (sentiment.py), so a failure here does not cost you the candles.
  7. upsert — Only the newly fetched rows are upserted, and any row still holding a NaN indicator is skipped rather than stored incomplete.

## Deep Historical Backfill (`backfill.py`)

A one-time operation to pull the maximum history KuCoin will give. Safe to
re-run — upsert semantics, per-token error isolation, resumable.

[diagram] The one-time deep fetch. Existing rows win every collision.
  - Determine start — Oct 2017 daily, Jan 2020 intraday (code in this repo)
  - Fetch all candles — paginated batches (something you do not control)
  - Load existing — OHLCV only (a database, table, queue or bucket)
  - Merge — existing wins on conflict (code in this repo)
  - Recompute indicators — over the full set (code in this repo)
  - Drop warmup rows — NaN out, FnG null (code in this repo)
  - Chunked upsert — 5K-doc batches (a database, table, queue or bucket)
  - Determine start -> Fetch all candles
  - Fetch all candles -> Load existing
  - Load existing -> Merge
  - Merge -> Recompute indicators
  - Recompute indicators -> Drop warmup rows
  - Drop warmup rows -> Chunked upsert

[flow] A deep backfill
  1. since — Oct 2017 for daily, Jan 2020 for 4h/1h, or whatever --since says.
  2. pull — Everything from that date is fetched in paginated batches.
  3. existing — What is already stored is loaded — OHLCV only, via load_all().
  4. merge — Deduplicated on timestamp, and existing OHLCV wins every conflict. This is why backfill CANNOT repair the pre-2026-07-19 truncated closes — it keeps the wrong row.
  5. recompute — Indicators are recomputed across the whole merged dataset, not just the new part.
  6. warmup — Rows whose indicators never warmed up are dropped, and Fear & Greed is set to None for history it does not cover.
  7. chunk — Written in 5K-document batches via bulk_upsert_chunked() so a large token cannot blow up the write.

## MongoDB Schema

- Database: `btc_data` (production), `btc_data_test` (testing)
- **Spot:** `{token}_daily_price_data`, `{token}_weekly_price_data`, `{token}_1h_price_data` — 17 each. Newer tokens (SUI/WIF) have partial indicators (SMA_200/EMA_200 null until ~200 weeks history).
- **Perp:** `{token}_perp_daily_price_data`, `{token}_perp_1h_price_data` — 17 each. No weekly (KuCoin Futures limitation). Perp 1h limited to ~15 months by exchange.
- **Funding:** `{token}_funding_rate_data` — 17 collections, raw 8h granularity.
- Each document keyed by `timestamp` (UTC); unique index enforced.
- `indicator_glossary` collection: auto-synced every pipeline run.
- `funding_rate_glossary`: per-token metadata (exchange, contract symbol, settlement schedule).
- **Production timeframes:** daily + weekly + hourly (17 tokens, spot + perp). 4h not in production.
- **Total:** ~110 collections.

Ecosystem collection naming contract: [../docs/shared/mongodb_contract.md](../docs/shared/mongodb_contract.md)

## Technical Indicators (~85)

Computed by `indicators.py` using `pandas-ta-classic`. Categories: Trend (SMA/EMA/Ichimoku/ADX/Supertrend/PSAR/Aroon), Momentum (RSI/StochRSI/MACD/Williams%R/CCI), Volume (OBV/CMF/MFI), Volatility (BB/Donchian/ATR/Squeeze), Risk (VaR/CVaR/Omega/Ulcer), ML Features (Z-scores/slopes/candle ratios), Sentiment (Fear & Greed).

Full list: [docs/INDICATORS.md](INDICATORS.md).

**Change protocol:** only edit `indicators.py`. Update `INDICATOR_GLOSSARY` for any column add/remove. Column names are a **public API** — coordinate with CRA before any rename (ADR-001).

## Known API Quirks

### KuCoin funding rate history — ~2-day dead zone

`fetch_funding_rate_history(since=T)` returns 0 records silently when `T >= (now − 2d)`. This is a KuCoin API behaviour, not a CCXT bug.

**Impact:** any incremental update that derives `since_ms` from a recent gap (e.g. yesterday's OHLCV date) will get 0 records and log nothing — invisible failure.

**Mitigation (implemented 2026-04-26):** `_get_funding_since_ms()` always starts 3 days behind the last stored funding timestamp. The 3-day window is outside the dead zone. Upsert idempotency handles the overlap. See `pipeline.py:_get_funding_since_ms`.

**Do not** replace this with a fixed lookback offset from `now` — the offset must be anchored to the last stored MongoDB timestamp to avoid re-fetching unbounded history on every run.
